# FishAdmin 2.2.0 — 组件成熟度矩阵 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把“React 版是否成熟”变成可执行、可回归的证据矩阵：83 个组件全部具备单测、全站 axe
门禁和逐组件视觉基线，并在文档站用 stable/beta 状态公开。

**Architecture:** `packages/ui/registry.json` 增加 `status`/`since`，新增
`scripts/maturity-core.mjs` + `scripts/check-maturity.mjs` 生成并校验
`apps/docs/generated/maturity.json`；文档站新增 `/guide/maturity` 渲染矩阵。单测按交互家族分四批
补齐；axe 全量扫描接入 PR；视觉基线按组件首个 demo 录制。

**Tech Stack:** React 19、Vite 8、TypeScript 5.9、Vitest 5、Testing Library、Playwright
1.64.1、Rspress 2、pnpm 9、Docker（`mcr.microsoft.com/playwright:v1.64.1-noble`）。

**Spec:** 本文件（设计与计划合一，沿用 `docs/plans/2.1.0.md` 的约定）；范围在 2026-11-03
与维护者确认：双主题视觉基线 166 张。

## Global Constraints

- 用户可见文档必须同时提供 `apps/docs/docs/en/**` 与 `apps/docs/docs/zh/**`。
- RBAC 仍是纯客户端实现；README / 权限页的安全边界免责声明不得弱化。
- 不引入后端、多租户或 SSO；模板定位保持企业级中后台。
- 组件运行时 API 不变。只有测试暴露真实缺陷时才做最小修复，并在 CHANGELOG 记录。
- 生成物（`maturity.json`、`rtl-audit.json`、API 页）必须入库并通过 `--check` 漂移校验。
- 视觉基线只能由 `mcr.microsoft.com/playwright:v1.64.1-noble` 生成。
- 提交、push、npm publish、tag、GitHub Release 各自需要单独批准；本计划只包含实现与本地验证。

## 关键决策

- **状态语义**：`stable` = 文档、demo、单测、axe、双主题视觉基线全部齐备；`beta` = 任一项
  缺失。初始 83 个全部标 `beta`，M5 按证据批量晋升；任何保留的 `beta` 必须写
  `statusReason` 并出现在文档里。`beta` 表示“证据未齐”，不表示 API 质量差。
- **矩阵是唯一事实源**：`check-maturity` 同时生成文档数据与 CI 门禁，状态不能手改绕过。
- **单测按行为而不是按覆盖率百分比补齐**：每个组件至少一个真实交互/语义断言；覆盖率只做
  地板，防止后续回退。
- **axe 全量进 PR**：预扫描证明零违规、成本约 2 分钟，不需要降级成 nightly。
- **视觉基线只截每个组件的首个 demo 区域**（`section[data-demo]` 第一个），不是整页、不是
  全部 167 个 demo；en、1440×900、light/dark，共 166 张。
- **`since` 先统一 `0.1.0`**（与现有文档一致），同时把 `ComponentMeta` 的硬编码版本改为读取
  registry；后续新增组件再按实际版本填写。

## 范围外

- Vue 3 包、消费端 tree-shaking/按需 CSS、真实业务页面扩展、changesets 自动发版、npm
  provenance、Dependabot 清理。
- 全部 167 个 demo 的视觉基线；只覆盖每个组件的首个 demo。
- 跨浏览器视觉基线（仅 Chromium）。
- 发布动作本身（commit/push/publish/deploy/tag/Release）。

- [ ] **Step 3: 实现 `maturity-core.mjs`**

```js
const EVIDENCE_KEYS = ['test', 'axe', 'visual', 'demo', 'docs']

export function evaluateComponent({
  entry,
  hasTest,
  hasAxe,
  hasVisualLight,
  hasVisualDark,
  hasDemo,
  hasDocs,
}) {
  const evidence = {
    test: hasTest,
    axe: hasAxe,
    visual: { light: hasVisualLight, dark: hasVisualDark },
    demo: hasDemo,
    docs: hasDocs,
  }
  const problems = []
  if (!hasDocs) problems.push('missing docs page')
  if (!hasDemo) problems.push('missing demo')
  if (entry.status === 'stable') {
    if (!hasTest) problems.push('missing test')
    if (!hasAxe) problems.push('missing axe coverage')
    if (!hasVisualLight || !hasVisualDark) problems.push('missing visual baseline')
    if (!entry.since) problems.push('missing since')
  }
  if (!['stable', 'beta'].includes(entry.status)) problems.push('invalid status')
  return {
    id: entry.id,
    name: entry.name,
    category: entry.category,
    status: entry.status,
    since: entry.since ?? null,
    statusReason: entry.statusReason ?? null,
    evidence,
    problems,
  }
}

export function summarize(components) {
  return {
    total: components.length,
    stable: components.filter((item) => item.status === 'stable').length,
    beta: components.filter((item) => item.status === 'beta').length,
    missingTest: components.filter((item) => !item.evidence.test).length,
    missingVisual: components.filter(
      (item) => !item.evidence.visual.light || !item.evidence.visual.dark,
    ).length,
    missingDemo: components.filter((item) => !item.evidence.demo).length,
    betaWithoutReason: components.filter((item) => item.status === 'beta' && !item.statusReason)
      .length,
  }
}

export { EVIDENCE_KEYS }
```

- [ ] **Step 1: 写 spec**

```ts
import fs from 'node:fs'
import path from 'node:path'

import { expect, test } from '@playwright/test'

const registry = JSON.parse(
  fs.readFileSync(path.resolve(process.cwd(), 'apps/docs/generated/registry.json'), 'utf8'),
) as { components: Array<{ id: string }> }

const appearances = ['light', 'dark'] as const

for (const component of registry.components) {
  for (const appearance of appearances) {
    test(`${component.id} ${appearance}`, async ({ page }) => {
      await page.addInitScript((theme) => {
        window.localStorage.setItem('rspress-visited', '1')
        window.localStorage.setItem('rspress-theme-appearance', theme)
      }, appearance)
      await page.goto(`/components/${component.id}`)
      await page.waitForLoadState('networkidle')
      await page.evaluate(() => document.fonts.ready.then(() => undefined))
      await expect
        .poll(() => page.evaluate(() => document.documentElement.classList.contains('dark')))
        .toBe(appearance === 'dark')
      await page.waitForTimeout(250)
      const demo = page.locator('section[data-demo]').first()
      await expect(demo).toBeVisible()
      await expect(demo).toHaveScreenshot(`${component.id}-${appearance}.png`)
    })
  }
}
```

- **50 个新测试可能暴露真实组件缺陷**：只做最小修复；修复进入 CHANGELOG；不因失败放宽断言。
  单个组件若受 jsdom 能力限制（chart、dropzone、sonner），用局部 mock 或保留 `beta` 并写
  `statusReason`，不写假测试。
- **视觉基线体积**：已确认双主题 166 张；预计 10–25MB。超过 35MB 时先压 demo 裁切范围
  （仍保留双主题），不改为整页。
- **视觉抖动**：只在 Docker 录制；`animations: 'disabled'`、字体 ready、主题 class 轮询、
  250ms 稳定期；组件基线只截 demo 区域，避开版本号。
- **CI 时长**：axe 增加约 2–4 分钟、UI 单测增加约 1–2 分钟、docs-visual 增加约 8–12 分钟。
  Docs E2E 若超过 15 分钟，用 Playwright `--shard` 拆成两个 job；docs-visual 若超过 20 分钟，
  按组件 id 分片。
- **状态膨胀**：`stable` 必须有证据；不允许为了让页面好看手改 JSON 绕过 `check:maturity`。
- **SSG/hydration**：矩阵页初始过滤状态用常量，渲染期不读 `window`。

### 偏差与处理

1. **stable 徽章对比度**：M5.1 把全部组件改为 stable 后，M1.1 起就存在的
   `.fish-component-meta__badge.is-stable { color: var(--primary) }` 在 light 主题下只有
   4.45:1（maturity 表的状态徽章为 4.49:1），低于 12.8px 文本的 AA 4.5:1，导致 166 条组件
   路由与关键页面 axe 全部失败。两处徽章改用 `var(--accent-foreground)`（light 7.4–7.5:1 /
   dark 13.3–13.7:1），并重录 button / pro-table / maturity 六个页面基线；组件 demo 基线不受影响。
2. **auth-shell 测试稳定性**：`src/features/auth/components/auth-shell.test.tsx` 的 `beforeAll`
   超时从默认 10 s 提到 30 s，避免冷缓存下的动态 import 在并行跑全量套件时偶发超时；仅测试
   代码，未改断言。
3. **组件基线重编码**：Docker 重录时 `label-dark`、`table-light` 被重写，逐像素比对只有
   2–3 个像素、单通道最大差值为 6（远低于 0.0002 的 `maxDiffPixelRatio` 容差），属于
   抗锯齿抖动；两张 PNG 已还原为提交版本，166 张组件基线保持不动。maturity 页文案调整后，
   两套页面基线再次在 Docker 中重录并通过干净运行（180/180）。
4. **beta 原因门禁**：README 曾承诺 `check:maturity` 会因 beta 缺少原因而失败，但门禁仅在
   汇总里计数。现在 `evaluateComponent` 对 `beta` 且无 `statusReason` 直接记问题，
   `check-maturity.test.mjs` 覆盖该分支；maturity 页与两份 README 的口径同步更新。
5. **CI 时长**：本地无法测量 CI 时长，需在 M5.3 push 后从 Actions 读取；本轮记录本地观测值
   （全量 axe 4.8 min，docs visual 5.9 min）。
6. **axe 证据口径**：`check:maturity` 的 axe 证据仍是"进入 documented 集合"的代理，尚未
   持久化逐组件扫描结果；这是 M1.2 起记录的设计取舍，全量扫描由 CI 的
   `DOCS_FULL_AXE=1` 负责。
7. **最终评审修正**：CHANGELOG 补齐 Progress / Skeleton / Spinner 三条真实缺陷修复；
   `versions.md` 改用 `Prepared` 口径，发布翻牌（Prepared → Live）列为 M5.3 的独立步骤；
   beta 的 `statusReason` 现在渲染在矩阵表状态列；`maturity-core` 删除未使用的 `EVIDENCE_KEYS`。
