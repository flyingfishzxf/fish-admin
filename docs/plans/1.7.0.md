# FishAdmin 1.7.0 — 看得见的能力计划

> 内部规划文档。本计划自身不面向终端用户；各里程碑产出的用户可见文档必须按仓库惯例同时提供
> `docs/en/` 与 `docs/zh-CN/` 两份，并保留 client-side RBAC 非安全边界的免责说明。

- 基线：`v1.6.0`（`origin/main` = `6bf1f8e`，annotated tag `v1.6.0` → `5e2095b`）
- 计划日期：2026-10-26
- 定位不变：**企业级中后台模板**。本计划不引入真实后端，理由见「范围外」。

## 目标

1.6.0 解决的是"接得进来、看得出能上生产"，代价是界面上几乎看不到变化。1.7.0 反过来，
只认三条判据：

1. 壳层能配 —— 布局可切、页签可开，刷新后还在。
2. 有"流程"这件事 —— 审批中心成为第一个带状态机的业务域。
3. 表格撑得住 —— 五千行不卡，分组表头与列固定可用。

## 现状与约束（数字取自 2026-10-26 的 `v1.6.0` 树）

| 门禁             | 现值                 | 预算   | 余量       |
| ---------------- | -------------------- | ------ | ---------- |
| `firstPaintJs`   | 170.6 KB（26 chunk） | 180 KB | **9.4 KB** |
| `largestAsyncJs` | 95.6 KB（`chart-*`） | 115 KB | 19.4 KB    |
| `totalJs`        | 749.4 KB             | 800 KB | 50.6 KB    |
| `totalCss`       | 22.8 KB              | 30 KB  | 7.2 KB     |

单测 83 文件 501 条；e2e 76 条；视觉 14 用例 / 16 张 Linux 基线。
首屏构成：`index-*` 94.7 KB、`utils-*` 23.6 KB、`matchContext-*` 19.0 KB、
`auth-store-*` 8.9 KB、`shim-*` 3.6 KB、`button-*` 3.5 KB，其余为小片段。

由此得到本计划最重要的一条结论：**9.4 KB 的余量养不起一个页签栏**。M1 的第一步不是写页签，
而是把只服务于 header 的 radix 片段移出首屏图；腾不出来就按 1.5.0 的 `c5a31aa` 先例改门禁定义，
但必须留下测量依据，不能凭感觉放宽。

其他事实：`_app` 下 21 个页面（另有 8 个认证页 + 4 个错误/维护页）、17 个 feature 域、
30 个 enterprise + 6 个 pro 组件、84 条 catalog（`usedIn` 门禁要求每条指向真实业务路由）、
`MOCK_DB_VERSION = 4`、21 个权限码、17 个菜单图标名、`src/stores/ui-store.ts` 目前只有 `commandOpen`。

## M1 — 壳层可配（约 3 天）

**问题**

- 壳层只有一种形态：侧边栏 + 顶部条写死在 `src/components/layout/app-shell.tsx`，
  企业客户里"顶部导航"和"紧凑密度"是高频要求，目前只能改源码。
- 没有页签工作台。中后台用户一天在十几个实体间往返，`ui-store` 里连"打开过哪些页"都没有，
  返回上一列表必然丢筛选。
- `firstPaintJs` 只剩 9.4 KB，而页签栏与布局偏好都要进壳层。

**任务**

1. **先腾预算**：`notification-bell`、`user-menu`、命令面板的 radix 片段改为按需加载
   （`matchContext-*` 19.0 KB 与 `utils-*` 23.6 KB 是主要目标），把 `firstPaintJs` 压到 ≤ 160 KB
   再开始写新功能；这一步单独一个 commit，先跑 `pnpm size` 再落地。
2. `ui-store` 扩成偏好存储：`layout: 'sidebar' | 'header' | 'mixed'`、`density: 'default' | 'compact'`、
   `contentWidth`、`followSystemTheme`，持久化沿用 `fish-admin:` 前缀（该前缀在 10 个文件里锁步，
   见 1.6.0 计划 M4 记录），设置页新增"界面"分区。
3. 多页签工作台：记录访问过的路由，可固定、右键"关闭其他 / 关闭右侧 / 全部关闭"，
   刷新按钮保留 query；页签列表持久化；**可达性判定复用 M5 的菜单树**，被服务端菜单隐藏的
   路径不留页签。
4. 锁屏与空闲超时（若 1 的预算腾不出来则顺延到 M4 之后，不硬塞）。

**验收**

- 新增 `e2e/shell.spec.ts`：切布局 → 刷新仍在；开三个页签 → "关闭右侧"后 URL 与 query 正确；
  viewer 角色登录后页签里不出现 `/components`。
- 壳层改动必然动像素：删除 16 张 Linux 基线后在容器里重录，再跑一遍证零 diff。
- `pnpm size` 四项绿，且 `firstPaintJs` 相比 M1 开工前不涨。

### 执行记录

**门禁（2026-10-27，跑在 M1 收尾的树上）**

| 门禁                                  | 结果                                                                    |
| ------------------------------------- | ----------------------------------------------------------------------- |
| `format:check` / `lint` / `typecheck` | 通过                                                                    |
| `test:coverage`                       | 85 文件 / 512 条；语句 78.09%、分支 81.04%、函数 70.40%、行 78.99%      |
| `test:e2e --workers=1`                | 79 条通过（含 axe、perf、security）                                     |
| `test:visual:docker`                  | 重录 16 张 Linux 基线后再跑一遍，14 用例零 diff                         |
| `size`                                | 首屏 170.9/180、最大异步 95.6/115、JS 753.7/800、CSS 22.9/30（均为 KB） |

**与计划的偏差**

1. 步骤 1「先腾预算」没有做，因为不需要。`dist/index.html` 的 modulepreload 清单里没有壳层代码：
   页签栏、布局切换、密度都随 `_app` 路由进 lazy chunk。计划正文「9.4 KB 的余量养不起一个页签栏」
   这条结论作废——页签栏根本不进首屏图，`matchContext-*` 也不必拆。
2. 但 `firstPaintJs` 仍从 170.6 涨到 170.9 KB（+0.3 KB）：`tabs.*` 文案写进了 `common.json`，
   而 `src/lib/i18n.ts` 静态导入 `common` 并让 Vite preload 它，en + zh 两份字符串恰好 +0.3 KB。
   没有为这 0.3 KB 单独拆命名空间：页签栏每次进壳层都要用这些文案，拆出去只会换来首屏后一次闪烁。
   所以「相比开工前不涨」差 0.3 KB 未达成，余量 9.1 KB，预算未破。
3. `followSystemTheme` 未放进 `ui-store`：`theme-store` 的 `mode: 'system'` 已经跟随
   `prefers-color-scheme`（`src/lib/theme.ts`），再存一份会多出一个状态源。设置页「界面」分区只暴露
   layout / density / contentWidth。
4. 锁屏与空闲超时未做，按计划「不硬塞」条款顺延。
5. 页签只保存 `to + search`（对应「待决 3」的倾向项），不缓存组件状态；刷新按钮用
   `queryClient.invalidateQueries` 重建当前页数据。
6. 验收里「viewer 页签里不出现 `/components`」改成不出现 `/roles`：两者都会被服务端菜单裁掉，
   但 `/roles` 直达会落 `/403`，一条用例同时证明「不可达路径不记录」和「403 不留页签」。
7. 页签栏是页面导航语义（`<nav aria-label>` + `aria-current="page"`），不是 `tablist`：
   axe 的 `aria-required-children` 会把没有 `tabpanel` 的 tablist 判成 critical。

**过程中修掉的问题**

- header 布局白屏：`Tooltip` 需要 `TooltipProvider`，原本只有 sidebar 布局的 `SidebarProvider` 提供；
  header 分支自己包一层 `TooltipProvider delayDuration={0}`。
- 页签菜单按钮的 aria-label 原为 `Actions for {{title}}`，与 rbac 用例里的行操作按钮重名，改成
  `More for {{title}}`。
- 空菜单不等于「全都不可达」：菜单请求未落时 `reachable` 为空，剪枝必须直接返回，否则每次冷加载
  都会先把持久化的页签清空再重建。
- `files.spec.ts` 在 720px 视口偶发超时：预览面板是 560px 的内滚动容器，底边在窗口外；搜索过滤后
  画廊（`images.length > 1`）消失让 `scrollTop` 被夹紧，触发器被推出窗口，popover 跟着落到屏幕外。
  用例改为 1280×1000 视口并注明原因，连跑 5 次全绿。

**未验证项**：锁屏 / 空闲超时（未实现）、页签的组件级 keep-alive（不做）。

## M2 — 审批中心（约 3 天）

**问题**

17 个业务域里没有"流程"：采购、请假、用印、变更在企业后台都走同一套"提交 → 多级审批 → 归档"，
而模板里最接近的只有审计日志（只读、无状态迁移）。缺这一域，"企业级"三个字只能靠组件数量撑。

**任务**

1. `/workflows`：我发起 / 待我审批 / 全部三种视图，query 过滤（状态、类型、发起人、时间范围），
   列表复用 M3 的虚拟滚动。
2. `/workflows/$id`：表单快照（`descriptions` + `json-viewer`）、时间线（已有 `timeline` 组件）、
   审批动作（同意 / 驳回 / 转交，走 `popconfirm`）、评论。状态机在前端表达，
   迁移合法性由 mock 处理器裁决，文档里写明真实后端必须重做这件事。
3. `MOCK_DB_VERSION` 4 → 5：新增 `workflow_instances` / `workflow_steps` / `workflow_comments`，
   v4 → v5 迁移保留既有用户、角色、会话与工作区数据。
4. 权限码 21 → 23（`workflow:read`、`workflow:approve`），接进路由、`<Can>`、权限矩阵；
   导航与 `GET /menu` 同步（icon 注册表 17 → 18 个名字）；catalog 里给流程相关组件补 `usedIn`。

**验收**

- `e2e/workflows.spec.ts`：待我审批 → 同意 → 实例状态与时间线更新 → 审计日志出现该记录 → 刷新仍在。
- viewer 看不到入口，且直达 `/workflows` 落 `/403`（复用 M5 的菜单判定，不新写一套）。
- 视觉基线 +2（列表与详情），双语 e2e 各跑一遍。

### 执行记录

**门禁（2026-10-27，跑在 M2 收尾的树上）**

| 门禁                                  | 结果                                                                    |
| ------------------------------------- | ----------------------------------------------------------------------- |
| `format:check` / `lint` / `typecheck` | 通过                                                                    |
| `test:coverage`                       | 85 文件 / 517 条；语句 74.36%、分支 76.21%、函数 66.57%、行 75.65%      |
| `test:e2e --workers=1`                | 82 条通过（原 79 条 + 审批中心 3 条）                                   |
| `test:visual:docker`                  | 18 张 Linux 基线（新增 2 张），16 用例零 diff                           |
| `size`                                | 首屏 171.7/180、最大异步 95.6/115、JS 764.8/800、CSS 23.0/30（均为 KB） |

**实现内容**

1. 数据层：`MOCK_DB_VERSION` 4 → 5，新增 `workflows` / `workflowSteps` / `workflowComments`；
   v4 → v5 迁移保留用户、角色、会话与工作区数据，并重新合并演示角色的权限码。种子 8 条申请
   （4 待审批、3 通过、1 驳回），由 `seed-workflows.ts` 按与处理器相同的规则回放决定。
2. Mock API：`GET /workflows`（mine / pending / all，状态、类型、发起人、日期、关键字、分页）、
   `GET /workflows/:id`、`POST /workflows/:id/decisions`、`POST /workflows/:id/comments`、
   `GET /workflows/approvers`。状态机、轮次校验、转交目标校验与审计事件全在处理器里。
3. 权限与导航：权限码 21 → 23，接进路由守卫、`<Can>`、权限矩阵；导航与 `GET /menu` 同步，
   icon 注册表 17 → 18（`workflow`）；catalog 把 `tabs` / `date-range-picker` 指向 `/workflows`，
   `timeline` / `popconfirm` 指向 `/workflows/$id`，组件总数保持 83。
4. 界面：列表三视图 + URL 过滤 + 分页；详情页表单快照、时间线、评论、处理面板（同意 / 驳回 /
   转交，均走 `popconfirm`）。转交候选来自 `/workflows/approvers` 并排除当前审批人。
5. 文档：`docs/en/workflows.md` 与 `docs/zh-CN/workflows.md`，写明接口契约、状态机、Mock 与真实
   后端的边界（事务、行锁、追加式时间线、按记录授权）以及客户端 RBAC 只是体验层。

**与计划的偏差**

1. 任务 1 写「列表复用 M3 的虚拟滚动」，但 M3 排在 M2 之后。本阶段先复用现有 `ProTable`
   的手动分页；虚拟滚动留给 M3，届时审批列表跟着换，不另写一套。
2. 计划只要求「状态机在前端表达，迁移合法性由 mock 处理器裁决」。实现把轮次归属、目标审批人
   资格也放进处理器，而不是只裁决状态迁移：否则转交可以把申请交给 viewer，时间线会自相矛盾。
3. 验收写「双语 e2e 各跑一遍」。没有把整套 e2e 复制成中英两份（运行时长翻倍），而是新增一条
   中文用例覆盖审批队列与详情的关键文案，其余用例保持英文；语言切换与持久化仍由
   `i18n-theme.spec.ts` 负责。
4. catalog 的 `usedIn` 不是新增条目，而是改指向：组件总数、`DEMOED_COMPONENTS` 与
   `CATALOG_DEMO_IDS` 的 83 条断言都保持不变；`components.test.ts` 的业务路由清单 6 → 8。

**过程中修掉的问题**

- 工作流文案最初用 `{name}` 单花括号，i18next 默认插值语法是 `{{name}}`，页面会原样渲染
  `{name} submitted the request`。en / zh 两个命名空间改为双花括号后由中文 e2e 覆盖。
- 详情页的 JSON 快照把 `amount` / `completedAt` 直接放进对象，缺值时 `JsonViewer` 会显示
  `undefined`；改为条件展开，原始载荷只含真实存在的字段。
- `components-catalog.spec.ts` 与 `components.test.ts` 都硬编码了 timeline 的 `usedIn`，改指向
  `/workflows/$id` 后同步更新，避免 catalog 演示与实际业务页脱节。
- v4 迁移测试原本把 `MOCK_DB_VERSION` 当作 v4 写进 fixture；版本升到 5 后该 payload 缺工作流数组，
  被判定为不完整并重置成种子。测试改为显式 v4 fixture + 新增 v4 → v5 用例。

**未验证项**：提交 / 撤回申请没有入口（计划未要求，种子数据提供「我发起」视图）；真实后端的
并发审批与事务语义只能由文档约束，Mock 无法验证。

## M3 — 表格撑得住（约 2 天）

**问题**

`pro-table` 目前一次渲染全部行：`/users` 六行看不出问题，五千行就是浏览器卡死。
列固定在分组表头下也不可用，而这是"订单/流水/台账"类页面的基本盘。

**任务**

1. 虚拟滚动（固定行高档，滚动容器对键盘可见，沿用 1.5.0 的 a11y 修复约定）。
2. 分组表头 + 列固定 + 列宽/列序持久化（复用现有列设置抽屉）。
3. mock 侧生成 5 000 行合成数据（客户端生成，不入库、不进 seed，避免撑爆 localStorage）。
4. `/users` 与 `/workflows` 打开新能力，其余表格保持默认关闭，避免一次性改动全部页面。

**验收**

- e2e 断言：5 000 行时 DOM 内行数 ≤ 80，滚到末尾仍可勾选与批量操作。
- perf 门禁（FCP / LCP / CLS / 请求数）不回退；`largestAsyncJs` 仍 ≤ 115 KB。

### 执行记录

**门禁（2026-10-27，跑在 M3 收尾的树上）**

| 门禁                                  | 结果                                                                        |
| ------------------------------------- | --------------------------------------------------------------------------- |
| `format:check` / `lint` / `typecheck` | 通过                                                                        |
| `test:coverage`                       | 85 文件 / 518 条；语句 74.33%、分支 76.35%、函数 66.57%、行 75.70%          |
| `test:e2e --workers=1`                | 83 条通过（M2 的 82 条 + 大数据集 1 条）                                    |
| `test:visual:docker`                  | 18 张 Linux 基线，16 用例零 diff（重录 users、workflows、audit-log 三张）   |
| `size`                                | 首屏 171.7/180、最大异步 95.6/115、JS 766.7/800、CSS 23.0/30（均为 KB）     |
| `e2e/perf.spec.ts`                    | FCP 48ms / LCP 944ms / CLS 0 / 首屏请求 100（预算 2500 / 3000 / 0.1 / 140） |

**实现内容**

1. `data-table` 增加固定行高的手动窗口化：`OVERSCAN` 6、`ResizeObserver` 观察视口、上下占位行、
   窗口起点按 `maxStart` 夹紧；滚动容器带 `role="region"`、`aria-label`、`tabIndex=0`，表格补
   `aria-rowcount` 与行 `aria-rowindex`。行签名（首尾 id）变化时滚回顶部，过滤后不会停在空窗。
2. 分组表头由列 `meta.group` / `meta.groupLabel` 推导，任一枚举列缺分组就整行不显示，避免半截
   表头；分组行与叶子表头在虚拟化时 `sticky`，叶子表头偏移固定为分组行高。表头背景改为不透明，
   滚动时不再透出内容。
3. 虚拟化时同时输出 `<colgroup>` 与 `table-fixed`，列宽、固定列偏移与表头才对齐；非虚拟化表格
   保持原有 `table-auto`，其余页面零改动。
4. `/users` 接分组表头、固定「选择 + 姓名」、`user-columns` 补 `group`；列可见性 / 顺序 / 宽度的
   持久化写入 `fish-admin:users-table-layout`。`/workflows` 接分组表头与固定标题列，列表随 M2 的
   三视图一起虚拟化（行高 64）。
5. Mock 新增 `synthetic-users.ts`：`faker.seed(5000)` 在内存生成 5 000 行，模板 id / 邮箱可预测，
   不写 IndexedDB、不进 seed；`/users?dataset=large` 才启用，强制 `pageSize=5000` 并隐藏分页，
   页头显示「演示数据集 · 5000 行」。该数据集上的批量改状态 / 删除 / 撤销只在处理器内存生效。
6. 测试与文档：`users-large-dataset.spec.ts` 断言 DOM 行数 ≤ 80、可滚到末行并批量改状态；列设置
   与列宽用例补「刷新后仍保留」断言；新增 `docs/{en,zh-CN}/tables.md`，README 功能列表与文档索引
   同步。

**与计划的偏差**

1. 没有引入 `react-virtual` 一类依赖，按计划允许的「固定行高档」手写窗口化：表格只需要单一
   纵向窗口，自写约 60 行即可，且不会增加首屏或异步包体。
2. 列宽 / 列序持久化只落在 `/users`（复用现有列设置抽屉）；`/workflows` 只固定标题列、不做
   抽屉。计划写的是「复用现有列设置抽屉」，审批列表本就没有该抽屉，硬加会扩大本次范围。
3. 大数据集做成显式 `?dataset=large` 开关，而不是让 `/users` 默认加载 5 000 行：默认演示、e2e
   选择器与既有 `localStorage` 体积都保持不变，也符合「其余表格保持默认关闭」。
4. 合成行的批量修改只存内存，刷新即还原。把 5 000 行或修改日志写进 IndexedDB 会让「不入库、
   不进 seed」的约束失效；文档已把这一点写成演示边界。

**过程中修掉的问题**

- 虚拟化表头最初沿用半透明背景，吸顶后能透出滚动内容；分组行与叶子表头改为 `bg-muted`，
  分组行显式给 32px 高度，吸顶偏移才稳定。
- 只加 `sticky` 不加 `<colgroup>` / `table-fixed` 时，固定列偏移按内容宽度计算，表头与表体错位；
  虚拟化路径同时固定布局后，1440px 下固定列左偏移为 0 / 44px。
- 滚到中部再过滤，旧 `scrollTop` 会落在新数据集末尾之外，窗口算出空数组；加入 `maxStart` 夹紧和
  行签名重置后，过滤与切换数据集都会回到顶部。
- 两组列宽合计在 1440px 下溢出（users 1158/1100、workflows 1146/1100），操作列被裁切；收窄
  姓名 / 邮箱 / 标题 / 时间列后，两者 `scrollWidth` 均等于容器宽。
- 保存过 `pageSize=10` 的视图再打开 `dataset=large`，分页被隐藏却只渲染 10 行；校验器改为只要
  `dataset=large` 就强制 5 000，并补了「显式传 500 也变 5 000」的单元测试。
- 审批分组名与列名都叫「状态 / State」；分组改为「类型与状态 / Type & status」「申请信息 /
  Request information」。

**未验证项**：真实后端的服务端分页、游标与按记录授权只能由文档约束，Mock 只在单页内过滤；
合成行的增删改不持久化是刻意取舍，刷新后回到种子状态；5 000 行以上（如 10k）的滚动性能未压测，
计划明确把数据量上限留给对接方。

## M4 — 字典与参数配置样板（约 1 天）

**问题**

企业后台几乎必有"数据字典 / 系统参数"，模板里没有，adopter 得自己想两级 CRUD 怎么摆。

**任务**：`/dictionaries` 左侧字典类型 + 右侧字典项两级维护，含拖拽排序、停用与引用计数提示；
`docs/{en,zh-CN}/` 补一节"照着抄"的范式说明，并接入 M5 菜单与权限矩阵。

**验收**：e2e 建/改/停一条字典项并在引用处看到它生效；`usedIn` 门禁指向新页；基线 +1。

### 执行记录

**门禁（2026-10-27，跑在 M4 收尾的树上）**

| 门禁                                  | 结果                                                                        |
| ------------------------------------- | --------------------------------------------------------------------------- |
| `format:check` / `lint` / `typecheck` | 通过                                                                        |
| `test:coverage`                       | 86 文件 / 527 条；语句 74.61%、分支 76.01%、函数 67.51%、行 75.99%          |
| `test:e2e --workers=1`                | 85 条通过（M3 的 83 条 + 字典 2 条）                                        |
| `test:visual:docker`                  | 19 张 Linux 基线（新增 1 张），17 用例零 diff（另重录 7 张导航受影响页面）  |
| `size`                                | 首屏 172.4/180、最大异步 95.6/115、JS 775.9/800、CSS 23.0/30（均为 KB）     |
| `e2e/perf.spec.ts`                    | FCP 52ms / LCP 916ms / CLS 0 / 首屏请求 101（预算 2500 / 3000 / 0.1 / 140） |

**实现内容**

1. 数据层：`MOCK_DB_VERSION` 5 → 6，新增 `dictionaryTypes` / `dictionaryItems`；v5 → v6 迁移补上
   三个系统类型与 16 个字典项并保留用户、角色、会话、协作与审批数据，v4 及更早沿同一链路迁移。
2. Mock API：类型列表 / 详情（id 或 code）、创建 / 改名 / 删除、字典项新建 / 编辑 / 删除、全排列
   排序；code / value 格式与同类型唯一性、种子保护、非空删除、被引用项禁止删除与改 value 全在
   处理器里，写入 `dictionary.created/updated/deleted` 审计事件。
3. 引用计数：只有 `user_tag` 接入演示页面，统计未删除用户中 `tags` 含该 value 的人数；类型计数为
   项计数之和。其余类型如实返回 0，页面标注「仅存档，尚无演示页面消费」，不伪造保护。
4. 界面：`/dictionaries` 左侧类型 + 右侧字典项。排序支持拖动把手与聚焦后方向键，焦点跟随被移动
   的行；状态开关写 `enabled`；引用大于 0 时 value 输入锁定；种子类型 / 种子项与仍被引用的项按
   规则禁用删除。
5. 消费闭环：用户详情标签建议读取启用的 `user_tag` 项并排除已选中标签，新增 / 改名 / 停用字典项
   会直接改变建议列表；`switch` 的 catalog `usedIn` 从 `/security` 改指 `/dictionaries`，组件总数
   与 83 条断言不变。
6. 权限与文档：权限码 23 → 25（`dictionary:read`、`dictionary:manage`），manager 两项、viewer 只读，
   `GET /menu`、导航、路由守卫与权限矩阵同步；新增 `docs/{en,zh-CN}/dictionaries.md`，README 功能
   列表、权限码数量与文档索引一并更新。

**与计划的偏差**

1. 计划只写「引用计数提示」，实现把计数做成硬约束：被引用项不能删除、value 不可改，只能停用。
   否则「编辑字典」会让用户资料里已保存的标签变成悬空值，提示就成了装饰。
2. 只有 `user_tag` 有真实计数，其余类型固定为 0。计划没有要求把字典接进所有业务域；给未接线的
   类型编一个计数会误导 adopter，文档明确写出了新增消费方时要改哪里。
3. catalog 没有新增条目，而是把 `switch` 的 `usedIn` 改指向新页；组件总数、`DEMOED_COMPONENTS`
   与 83 条断言保持不变，`components.test.ts` 的业务路由清单 8 → 9。
4. 类型 / 字典项的选中态不写入 URL。M4 只有一个主从面板，刷新后默认选中第一个类型；需要深链时
   再引入 `?type=`，避免为单页面提前增加路由状态。

**过程中修掉的问题**

- 三个种子类型最初共用同一个 `createdAt`，列表按名称排序后默认选中「Approval priority」，e2e 与
  用户预期都落在「User tags」；改为每个类型递增一分钟，默认选中顺序稳定。
- 权限分组新增 `dictionary` 后，`locales.test.ts` 立刻报 `permissions:groups.dictionary` 缺失；
  en / zh-CN 两个 `permissions.json` 补上分组名。
- 字典功能新增的 `api.ts` / `queries.ts` 未测试，函数覆盖率从 66.57% 掉到 62.69%，低于 65% 阈值；
  补了 9 个接口函数的客户端测试与 query-options / 启用项过滤测试后回到 67.51%。
- e2e 最初点击标签建议后再验证改名，但选中标签后建议会按设计从列表移除；用例改为只断言建议
  可见，改名与停用仍能验证消费端读取的是字典。

**未验证项**：HTML5 拖拽的指针路径没有 e2e（方向键排序与刷新持久化已覆盖，拖拽与键盘共用同一次
reorder 请求）；自定义类型的创建 / 删除只有界面与客户端测试，e2e 只覆盖字典项闭环；真实后端的
事务、唯一索引、引用计数查询与按租户收窄读取只能由文档约束；中文界面下字典页未有专门 e2e，
语言切换本身由 `i18n-theme.spec.ts` 负责。

## 范围外（写清楚，避免下一轮又滑回去）

- 真实后端、多租户、SSO/OIDC：模板的价值就是不绑后端，见 1.6.0 计划「参照系结论」。
- 服务端分页与游标、10k 行压测：M3 只做客户端渲染能力，数据量上限由对接方决定。
- 可观测性服务端：最多做到前端把 Web Vitals 与错误交给一个可替换的 sink，默认只 `console`。
- 表单设计器、文档站、移动端完整适配、第三语言：推到 1.8.0 及以后，本轮不与壳层改动挤在一起。
